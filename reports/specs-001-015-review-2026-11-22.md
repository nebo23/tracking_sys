## Findings

P1 findings affect financial integrity, privacy, or multi-agency isolation. P2 findings produce incorrect results or failed requests in the stated conditions. The companion [regression patch](specs-001-015-review-regressions.patch) contains expected-behavior assertions; they are deliberately failing regressions against the reviewed implementation, not production fixes.

### R001 P1 Unsigned Paymob fields change verified financial evidence

The HMAC field list excludes `is_live` and `parent_transaction`, but both control the posting decision. With an otherwise authentic synthetic callback and its unchanged signature, changing `is_live` from false to true turns a test transaction into a verified EGP 1,000 sale. Changing a refund's unsigned `parent_transaction` points the accepted adjustment at another sale of the same client. The signed child flags establish the operation's shape, but they do not authenticate which sale it adjusts or whether it is live.

This requires possession of a valid signed callback and its callback destination; it is not HMAC forgery from an arbitrary unsigned body. Entry-review note N1 acknowledges unsigned fields, but its signed-flag condition does not prevent either reproduced case. Authenticate these financial properties independently, or keep evidence unverified when the provider's signed data cannot establish them. Do not simply append fields to the HMAC algorithm, because that would reject provider signatures.

Source: [Paymob field list and mapper](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/payments/paymob.py#L259). Regressions: `test_review_test_payment_cannot_become_verified_with_same_signature`, `test_review_refund_cannot_be_retargeted_with_same_signature`.

### R002 P1 A linked booking prevents subject erasure

Create a subject with attribution consent, accept a booking containing its subject token, then erase the subject. PostgreSQL raises `CheckViolation` for `ck_bookings_valid_link`. The foreign key sets `bookings.subject_id` to NULL, while `linked_at` remains populated; the check requires both to be NULL together. The erasure transaction rolls back, so neither the subject deletion nor the other changes in that transaction complete.

Detach both fields atomically under the privacy lock before deleting the subject, and cover lifecycle deletion as well as the explicit erasure path. Preserve restricted runtime/lifecycle grants in the chosen correction.

Sources: [booking constraint and foreign key](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/models/integrations.py#L161), [subject deletion](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/services/collection.py#L659). Regression: `test_review_linked_booking_does_not_block_subject_erasure`.

### R003 P1 Booking attribution survives consent withdrawal

Link a booking while attribution consent is granted, then withdraw that consent. The booking remains linked and the report still returns `totals.linked = 1`. `_link` checks consent only when creating the link; reads use the presence of `subject_id` alone. This contradicts D-068 E4's condition that a booking is linked only while attribution consent is granted.

Remove or suppress the link when consent is withdrawn or expires, and make every consuming read respect the current consent state. Cover expiry and concurrent deliveries as well as withdrawal.

Source: [link creation](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/services/integrations.py#L391) and [linked count](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/services/integrations.py#L531). Regression: `test_review_booking_link_stops_on_withdrawal`.

### R004 P1 WhatsApp routing trusts an unproven number claim

An agency Owner can submit any unused numeric `phone_number_id` for a client and immediately create an active routing entry. Neither registration nor callback routing establishes that this agency controls the provider number. A different agency that knows a number ID can claim it before its legitimate onboarding; authentic notifications subsequently delivered to the shared Meta app are stored under the claimant's client. The global uniqueness constraint also prevents the legitimate client from registering it later.

Agency authorization is checked, but ownership of the external asset is not. The regression uses a second agency and a legitimately signed synthetic provider notification; the claimant does not need the Meta app secret. Add a verified asset-to-client binding or a trusted platform approval step before activation. This requires an explicit onboarding design decision within the multi-agency security boundary; it must not be treated as an arbitrary live provider call authorized by this review. The current off-by-default gate limits exposure until enabled.

Sources: [immediate activation](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/services/whatsapp.py#L54), [routing lookup](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/services/whatsapp.py#L122). Regression: `test_review_whatsapp_number_requires_ownership_before_routing`.

### R005 P2 An invalid Paymob callback produces HTTP 500

Send `{"type": [], "obj": {}}` with a syntactically valid but incorrect 128-character HMAC to a synthetic source. The response is 500 instead of the documented uniform 401. `parse_body` performs set membership on an unhashable list before verifying the signature. An object in `type` has the same issue.

Validate the discriminator's type before membership and retain the uniform refusal response without persistence. Source: [parser](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/payments/paymob.py#L173). Regression: `test_review_malformed_unsigned_callback_stays_401`.

### R006 P2 Independent booking sources merge unrelated identifiers

Create two signed webhook sources for the same client and submit each tool's local booking ID `booking-1`. Only one booking remains. Chain discovery scopes IDs by client and provider kind, so all generic booking tools share the `signed_webhook` identifier namespace. A reschedule or cancellation from one tool can therefore affect another tool's booking.

Scope booking identities and chain joins to the source or an explicitly shared provider-account namespace. Preserve intentional duplicate delivery handling within that namespace. Source: [chain discovery](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/services/integrations.py#L403). Regression: `test_review_two_booking_sources_do_not_merge_local_identifiers`.

### R007 P2 CRM verification depends on delivery order

Send a 09:00 stage event containing a valid payment reference and amount, followed by a 10:00 won-stage event omitting those optional fields. The deal becomes `won_verified`. Deliver the same two events in reverse order and it becomes `won_unverified`: the older event is discarded entirely, so its payment reference is never retained. The latest stage is correct in both cases, but the financial linkage differs.

Define optional-field semantics consistently and derive their latest supplied values independently of stage order, or require complete event snapshots. The same logical event history must produce the same result. Source: [older-event return and optional updates](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/services/integrations.py#L589). Regression: `test_review_crm_payment_evidence_survives_out_of_order_events`.

### R008 P2 CRM totals silently exclude deals after the first 500

With 501 open deals, `GET .../crm/deals` reports `totals.open = 500`. The query limits the selected deals before computing totals, and the response provides no continuation or truncation indicator. Older won and lost deals also disappear from the aggregate.

Compute aggregates over the full authorized scope separately from the detail page, and make detail pagination explicit. Source: [limited query and totals](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/services/integrations.py#L703). Regression: `test_review_crm_totals_cover_more_than_500_deals`.

### R009 P2 One malformed WhatsApp message rejects a valid batch

The parser's checks do not cover all accepted JSON shapes. A signed notification containing `referral.source_type = []` raises `TypeError`; a 12-digit timestamp beyond Python's supported date range raises an exception in `datetime.fromtimestamp`. Both requests returned HTTP 500 in the reviewed Windows environment. Parsing the complete list occurs before persistence, so a valid second message in the notification is lost with the malformed one. This is a robustness failure on verified provider input, not an unauthenticated signature bypass.

Validate scalar types and timestamp range, and isolate an invalid message so valid messages in the same notification can be accepted according to the documented acknowledgement contract. Sources: [timestamp conversion](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/integrations/whatsapp.py#L68), [source membership](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/integrations/whatsapp.py#L87). Regression: `test_review_whatsapp_malformed_message_does_not_discard_valid_batch`, two cases.

### R010 P2 Advertising pagination loses a currency group

Store two supported facts for the same ad on different dates, one in EGP and one in USD, and read with `limit=1`. The first page returns EGP and cursor `111`; the next page is empty, so USD is unreachable. Groups are ordered by `(object_id, currency)`, but the cursor and filter use only `object_id`. D-064 D4 explicitly preserves each fact's currency when account metadata changes, making this an allowed stored-data condition.

Use a cursor containing the complete grouping key. Source: [page selection](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/services/advertising.py#L136). Regression: `test_review_ad_spend_pagination_preserves_both_currencies`. This defect is already present in merged Spec 014.

### R011 P2 Instagram skips a historical day across midnight

With a fake provider clock at `2026-11-21T23:59Z`, fetch the account stream at its 729-day history boundary. Advance the clock by two minutes and resume using the returned cursor and unchanged requested bounds. The pages contain `2024-11-22` and `2024-11-24`, skipping November 23. The numeric cursor indexes a day list whose first day is recalculated from the current clock on each request.

Use a stable absolute day cursor or persist the original bounded start. This is the previously documented Spec 010 follow-up, independently reproduced here, not a new Spec 015 regression. Source: [rolling boundary and cursor](https://github.com/nebo23/tracking_sys/blob/db750d1b728f2ca352a999afe71c92a1b10730e1/backend/app/connectors/instagram.py#L448). Regression: `test_review_instagram_cursor_does_not_skip_day_at_midnight`.

## Repository and operational follow-ups

- **No checked-in CI workflow was found.** The reviewed PR head had no returned commit statuses. Local evidence is useful, but automated merge checks should run the pinned backend, PostgreSQL and tracker suites when CI is introduced. This review did not inspect branch-protection settings.
- **Setup documentation is stale.** The final README still says migration `0016_youtube_provider` and an 88-operation API. The final PR actually ends at `0025_whatsapp`, with 121 operations across 99 paths in the contract. `backend/README.md` still describes the Spec 002 baseline. Reconcile these before giving setup instructions to another developer; do not apply migrations to the native database as a documentation fix.
- **The main checkout is older than GitHub.** The root checkout was at `5d05153`; GitHub main was `73efae9`. The review used explicit commit archives instead of silently changing the owner's branch. PR 13 correctly targets the current merged main and is mergeable according to GitHub, which says nothing about functional correctness.
- **Ledger reads have a scaling risk.** `client_ledger` loads all evidence, and `calculate` rebuilds each arrival prefix to produce its journal. A synthetic local probe of `calculate` took approximately 0.096 seconds for 100 records, 2.383 seconds for 500, and 15.249 seconds for 1,000. These are workstation observations, not a controlled benchmark or an SLO. A 10,000-row CSV import is permitted, while the read response limit is applied after calculation. Measure realistic workloads and address the repeated work before production; persisted journal changes remain part of the separate 007-B review.
- **Known external checks remain open.** Instagram refresh/access-removal and App Review follow-ups, YouTube Phase 4 and the documented secret-rotation steps, live Meta Ads/CAPI, Paymob, Cal.com and WhatsApp checks, HTTPS hosting, native rollout and production operations remain as recorded. No credential was inspected or rotated during this review.
- **Secret screening was limited.** Targeted current-tree scans found no private-key headers or the selected token patterns; tracked history filenames did not include `.env`, `.env.docker`, PEM/key files or `local-data` contents. This does not replace full secret-history scanning or dependency advisory analysis.

## Using the regression patch

Run `python -m pytest tests/test_review_instagram_cursor.py -q` from `backend/`. Run `python -m pytest tests/integration/test_review_001_015.py -q --tb=short` with the repository's explicitly enabled disposable-database configuration. The original repository guard expects port 55433; this audit used 55434 only in its private snapshot to avoid the other session's database. Never point these tests at native `tracking_sys`.

Prioritize the P1 corrections and their regressions, then the reporting/parser corrections. Any new schema or external-ownership workflow should follow the existing decision gates. This review does not authorize publication or merge.
