# Specification 006 decision packet

Revised 2026-11-11 for [design revision 3](design.md), after two reviews of the preparation (published head `b9801de`, then revision 2). All D1–D13 items remain proposals. Approval applies to the named items in design revision 3. The [verification matrix](verification-matrix.md) gives the acceptance cases. The [review register](preparation-review.md) identifies the recommendations that changed and maps every finding to its sections and cases.

Approving a recommendation approves local implementation with synthetic data and disposable databases only. Push, pull request, merge, native `tracking_sys` migration, real customer intake and deployment remain separately gated.

## Group B: identity policy

| ID | Recommended option | Practical alternative | Consequence of each |
|---|---|---|---|
| D2 Evidence and automatic linking | Automatic links only from **trusted assertions** sent with an ingest key, with an allowed method for that identifier kind and `verified_at` within **30 days**. Keys join only when co-asserted in one assertion. The engine never merges existing persons. This expands a client-granted ingest credential's write authority to include assertions. Acknowledgements disclose no person ID, matching outcome, or deletion or objection history (design section 12.2). Browser forms, campaign links, devices and IP addresses never link. No webhook assertions in 006 v1. | Also accept unverified contact values (for example a lead-form email) as automatic links when they match an existing verified key. | Recommended: fewer false merges and a clear evidence chain, but lower recall (Outcome B in design section 2.2). Alternative: more connected journeys, but anyone typing another person's email attaches their visits to that person's timeline, which violates acceptance criterion 2. |
| D4 Phone normalization | `phone:v1` = international ASCII input only: after trimming ASCII spaces the input must match `^(\+\|00)[1-9][0-9 ()-]*$` with 8–15 digits (design section 5). Validate before canonicalization, domain-separate matching versions in the HMAC input and retain applicable versions for deletion checks. National input is rejected with `phone_country_required` and other invalid input with `identifier_invalid`. The candidate trunk-zero rule is not used. | (a) Add a per-client default country with the trunk-zero rule (new client column). (b) Add a phone-number parsing library (new dependency) with an explicit per-assertion country. | Recommended: no false merges from country guesses or stray characters; senders must convert to international ASCII form. (a) Merges a Saudi or UAE mobile with an Egyptian landline, mishandles Italian numbers, and false merges cannot be undone without the raw values (design section 5.1, observed on merged code). (b) Correct parsing, but a dependency and metadata update cycle needs its own approval. |
| D5 Conflicts and shared devices | Rules R1-R5 and the segment model of design sections 4.2-4.4: contested keys, an ambiguous outcome with a review queue and an ambiguous segment, `customer_ref` authoritative within its client (one per person), phones as weak anchors that never pull a new email or `customer_ref` into a person (R2-P), a contested key supplies no anchor even alongside new keys, pre-identification events ambiguous on shared devices, cross-boundary late events ambiguous. Persist closed segment bounds and a monotonic identity floor, so erasure, expiry, merge and unmerge never extend a segment. Classify each event as confirmed, excluded or unresolved for a person. Call tracker `restart()` on known sign-out or account switch. On a shared site without a reliable switch signal, restrict person-level association to verified account interactions. | Treat any second person on a collection subject as making the whole subject ambiguous (no segments). | Recommended: shared devices keep usable journeys without transferring visits between people. Alternative: simpler code, but a shared family browser loses all attribution after one switch. |
| D13 Lead and customer stages | Design section 4.5: lead requires a **trusted** `lead_signal`; customer requires **verified sale evidence from 007**; browser lead signals and trusted purchase signals are flags only. | Treat any lead_signal as a lead and a trusted purchase_signal as a customer until 007 exists. | Recommended: stage counts are evidence-backed and do not change meaning when 007 arrives. Alternative: earlier "customer" numbers that 007 would later contradict. |

## Group C: consent, handoff and deletion

| ID | Recommended option | Practical alternative | Consequence of each |
|---|---|---|---|
| D3 Identity handoff and issuance | One-time handoff code from the tracker (`identityHandoff(challenge)`) bound to a unique challenge from the backend's verified form/login transaction, 10-minute lifetime, single use, issued only with effective `identity_link` and only for `browser`-issued subjects, redeemable only with the client's ingest key. Direct assertion by bearer token requires `server` issuance and the current identity grant receipt. The six-cell matrix of design section 8.1 applies; legacy `unknown` subjects use neither route. | (a) Expose the subject token to the host page so the client's backend can send it directly. (b) Permit the browser handoff for legacy `unknown` subjects. | Recommended: one small public route and table, no browser subject token crossing into the client backend, and no public route for a server-held token. Legacy subjects cannot be linked: browser visitors regain linking at their next grant after the 24-hour local token lifetime, and server senders need fresh consent for a new subject. Without real intake before 0009, this affects development data only. (a) No new route, but a reusable subject credential that can change consent and erase data spreads into client backends and logs. (b) Current browser sessions stay linkable, but a legacy server-held token could be linked through the public route without server-issuance proof. |
| D6 Retrospective linking | R-B: a link covers events of that collection subject received at or after its `identity_link` grant, including events before the assertion, as long as no segment closure or erasure occurred on the subject during that grant (the identity floor, design section 4.4). | R-A: all retained events of the collection subject. R-C: only events received after the assertion. | R-B: in the usual one-banner flow the whole session links, nothing collected before identity consent is linked, and no later link reaches back over another person's interval. R-A links data collected without identity consent. R-C loses the campaign landing that preceded sign-in, which is the main value of cross-device attribution. |
| D7 Withdrawal, expiry and erasure | **W1**: withdrawing or explicitly denying `identity_link` deletes that collection subject's segments, assertions and handoffs immediately, raises its floor, and removes persons and keys left without evidence. On **expiry**, nothing new is linked and earlier assignments stay until their events expire. **Erasure** follows design section 7: an ambiguous identity lookup or active merge pauses the request before any deletion; a subject is erased whole only when exclusive to the person; on a shared subject confirmed events are erased, excluded events survive, and unresolved events are held with the request `on_hold` until an Owner/Admin decides to erase or retain them. A token-holder erasure remains limited to that collection subject. New tombstone types `identity_key` (over the pseudonym), `assertion_id` and `assertion_request`. Tombstone outcomes stay internal; the write API answers as for a live assertion. | **W2**: withdrawal stops new links but keeps past links for history. For erasure on shared subjects: erase unresolved events automatically. | W1 matches the 003 propagation rule (linking stops; without another basis, delete) and leaves no linked history the visitor objected to. W2 keeps fuller history for attribution, but continued use of withdrawn linking needs a legal basis the owner must document. Holding unresolved events neither erases another person's possible data nor keeps possible data of the requester silently, but each such erasure needs a manager decision. Automatic erasure completes immediately, at the cost of anonymous events that may belong to other people. |

## Group D: access and corrections

| ID | Recommended option | Practical alternative | Consequence of each |
|---|---|---|---|
| D8 Who may read person-level data | Owner/Admin for all clients; Analyst and ClientViewer only with a new per-client `can_view_identities` grant flag (default off), like the financial flag, carried through grant writes, invitations, acceptance, legacy updates and live revocation. No service read-key access in v1. | Any principal with `client:read` sees profiles and timelines. | Recommended: person-level journeys are opt-in per member and client; one schema flag on two grant tables. Alternative: no schema change, but every existing analyst and client viewer immediately sees person-level journeys. |
| D9 Contact values | Store keyed identifiers only. Profiles and the lead inbox show identifier kinds and verification methods, **never values or masks**. Follow-up uses the client's own CRM. The 004 form classes stay unchanged. | Store sealed raw contact values and add a contact-view permission so the lead inbox can show them. | Recommended: no reversible contact store, smallest breach impact, no new key custody. Alternative: a more useful inbox, but new high-sensitivity storage, a display permission, export rules and Q-012 retention, all of which need review. |
| D10 Merge and unmerge | Owner/Admin only, with closed reason codes and both participants' expected correction versions. Disjoint pointer-merge pairs in v1, evidence-anchored associations, merge-dependency markers on keys and links created from evidence that spans both sides, reversal of the named active edge with R5 re-evaluation of dependent items and ambiguous items sent to review, idempotent operation IDs whose exact retries return the recorded result, atomic increments of both participants' versions and journey revisions, active edges reversible without an age limit, and the `identity_changes` feed with a consistent rebuild contract for 007/008. | Physical merge that rewrites keys and links to the survivor and keeps a history table. | Recommended: unmerge is exact and cheap, original evidence is never edited, and devices that depended on the mistaken merge leave both timelines. The retention cost is stated under D12. Alternative: simpler reads, but reversal must replay history and loses links created during the merge window. |

## Decisions that actually block the next step

**006-A (the full 0009 migration)** depends on D1–D12, because the migration encodes a choice from each of them:

| 0009 element (design section 12.1) | Decisions it encodes |
|---|---|
| `identity_key_secrets`, key bytes and normalizer labels | D4, D9, D11 |
| `identity_assertions`: evidence, fingerprint and internal outcomes | D2, D7 |
| `identity_handoffs` with unique code and challenge digests; `collection_subjects.issuance_channel` | D3, D11 |
| `identity_links` owned and ambiguous segments; `identity_floor_at` and `identity_shared_at` | D5, D6, D7 |
| Tombstone types `identity_key`, `assertion_id`, `assertion_request`; deletion targets and audit actions | D7 |
| `can_view_identities` on `client_grants` and `invitation_client_grants` | D8 |
| No raw contact columns | D9 |
| `identity_merges` status and versions; merge IDs on keys and links; `version` and `journey_revision` | D10 |
| `identity_changes` and `identity_feed_state` | D10, D11 |
| Data-policy classes, lifecycle privileges and retention | D12 |
| Slice order and scope | D1 |

A partial selection permits only independent preparation until the affected schema choices have been reviewed.

- **006-B** depends on 006-A. **006-C** also requires D13 for stage semantics.
- **006-D** depends on 006-C. Tracker-only checks in **006-E** depend on 006-B, and its end-to-end timeline check depends on 006-C.

Approving Groups A to D as recommended authorizes all five slices locally. A partial approval should name the groups or items approved, and the slices then stop at the first unapproved dependency.
