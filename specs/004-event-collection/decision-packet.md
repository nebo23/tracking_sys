## Decisions for 004

| ID | Recommendation | Alternatives and consequences | Blocks |
|---|---|---|---|
| D1 Scope and slices (C004-01) | Fixed v1 event types (`page_view`, `link_click`, `form_submit`, `lead_signal`, `purchase_signal`); trusted server intake first, then public browser intake and one generic HMAC webhook, then deletion, lifecycle and diagnostics. Bot/internal traffic is labeled and stored, never retained as IP or user agent. No SDK, React, broker, paid provider, named adapter or new dependency. | Client-registered custom event types now: more schema and admin surface. A named provider adapter first: needs that provider's contract and configuration. Dropping, rather than labeling, bot traffic hides false positives. | All 004 work |
| D2 Write authority (C004-02) | New immutable credential kind: existing and default keys are `read`; an `ingest` key can only write events and record API consent for its granted clients, with no client or financial read. | Write flag on the existing grant: simpler, but every ingestion key also gets client read access, and its blast radius grows. Source-bound ingestion keys: tighter binding, but a second credential lifecycle (liveness, expiry, revocation) to build and test. | 004-B schema; 004-C route |
| D3 Subjects and consent binding (C004-06a) | A subject token exists only after an explicit consent grant (public consent route, or trusted API consent). Every 004 event needs a live subject with current consent for its purposes. The server derives and stores the consent basis, so no client-presented receipt exists to substitute. Grants are valid 12 months. | Client-presented receipt verified against client and subject: more input to validate, and a stale receipt still cannot be trusted over current state. Anonymous events without a subject: incompatible with J1 strict opt-in for non-necessary purposes. Consent validity of 6 months or no expiry: re-prompting cost versus stale consent. | 004-B; 004-C admission |
| D4 Field and data-class matrix (C004-07, new) | Design section 5: minimized URLs; `utm_*` with analytics; click identifiers only with attribution; registered forms whose mapped fields are option, code or quantity classes. No free text, email, phone, name or address in 004; they move to 006, which can delete by keyed identifier. | (b) Allow identifiers and free text now: needs keyed identifier indexes for deletion by email or phone, and an identity policy that overlaps 006. (c) Form key only, no field values: simplest, but omits the PDF-004/008 field mapping. | 004-B forms table; 004-C validation; M5 |
| D5 Deduplication and conflicts (C004-03) | Unique `(client, event_id)`. An identical copy is a duplicate. A different copy is a conflict (counter only, no retained content). A public-to-trusted copy with the same type and subject upgrades the row (new revision, first receipt time kept). Equal-trust disagreement is a conflict; public input never overwrites. | Reject every divergent copy (no upgrades): simpler, but server enrichment cannot correct browser claims. Neither option treats a purchase signal as revenue. | 004-C |
| D6 Limits (C004-04) | Keep the existing 16 KiB body bound (replacing the draft's 64 KiB); one event per request; 32 form fields; 2,048 characters per string and URL; +5 minutes skew; 7 days lateness; 5-minute webhook window; 60/min per browser source and peer, 600/min per ingest key or webhook source; Retry-After. | 64 KiB events: a per-route middleware change. Batches: partial-failure semantics and larger transactions. Different rates need Q-004 workload inputs. These are development values, not capacity commitments. | 004-C, 004-D |
| D7 Retention (C004-05) | Event rows (payload and receipt) 13 months, provisional for development and synthetic use, with Q-012 reopened before real intake. Diagnostic counters 30 days. Subjects and consent records 13 months after last activity, or on erasure. Previous webhook secret 24 hours. Subject tombstones (D-025), replay tombstones and deletion requests for the workspace lifetime. No separate lifetime receipt store: design section 12 explains why the 7-day lateness bound keeps honest retries deduplicated after expiry. | 30-day payloads (first draft): less retained data, but no lookback or year-over-year attribution. 25 months: longer history and more personal data. Lifetime digest receipts (first draft): unbounded growth with no extra protection for honest senders. | 004-B registry; 004-E lifecycle |
| D8 Schema and privileges (C004-06b) | Migration `0007_event_collection` with the nine tables of design section 11, `service_credentials.kind`, extended audit checks, the listed runtime grants (consent records and tombstones never updated; delete only for erasure stores) and lifecycle grants (events, counters, subjects, consent, secrets; never tombstones or requests). The downgrade refuses populated state. | The first draft's inventory (separate lifetime receipts, event-schema table, deletion-target table) adds three tables without a v1 need. Granting the lifecycle role tombstone access would let retention erase replay protection. | 004-B |
| D9 Key custody (C004-06d) | Webhook secrets sealed under the D-025 local token keyring (adds `webhook_signing` to `SecretContext.kind`). A new independent local tombstone keyring with key IDs on rows and add-only rotation. Digests for subject tokens and ingest keys; public keys are non-secret. Development only; production custody with 020. | Webhook secrets derived from one master key: no stored ciphertext, but provider-generated secrets (later adapters) would still need storage, leaving two mechanisms. Per-client keys for crypto-shredding now: belongs to 017 offboarding (D5). | 004-B settings; 004-D webhook; 004-E deletion |
| D10 Concurrency (C004-06c) | One transaction-scoped advisory lock per client (two-key namespace 4004) for ingestion, consent changes, deletion and lifecycle expiry. Scope is re-resolved after the lock; a 2-second lock timeout returns 503 with Retry-After. | Per-subject locks: more throughput, but a replay presented with a different subject can race with deletion unless an additional event-ID lock design is added. Revisit with Q-004 evidence. | 004-C onward |
| D11 Deletion surface (C004-08, new) | Synchronous erasure by Owner/Admin (subject token or event ID) and by the token holder through the public route (`data_subject` added to `RequesterKind`). Tombstones for the subject and each deleted event ID. No journal outbox in 004; append-only tables allow 019 to backfill the journal. | Admin-only erasure: the tracker (005) could not offer self-service. An asynchronous job: needs scheduling (Q-009). A journal outbox now: no protection until 019 ships it off-database. | 004-E |
