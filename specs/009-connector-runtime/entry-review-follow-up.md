# Spec 009-A entry review follow-up

Reviewed commit `e140d79` on `codex/spec-009-connector-runtime`. This is a recommendation for the owner's decision. The proposed scope is D1–D10 in the [entry review](entry-review.md#7-decisions-for-009-a), with the following clarifications. The five-table scope, synthetic provider, one-page sync and existing dependencies are sufficient to proceed once the owner selects this proposal.

| Decision | Clarification for implementation | Acceptance evidence |
|---|---|---|
| D2, D3, D5, D7 | Bind reconnect to the tenant, connection and generation at initiation. Recheck the expected state and generation before activating it. Apply the same check before installing tokens from refresh. A provider grant survives a local SQL rollback. Define how to dispose of newly issued synthetic credentials when a callback loses a race, a duplicate account insert fails, or saving the grant fails. Cleanup must target the discarded grant alone. | Race a pending reconnect and a pending refresh against disconnect. Also exchange two independent authorization codes for the same client/account. Assert the final connection state, exactly which grants remain usable at the provider, and that a different client's grant still works. |
| D3 | The documented flow uses `state` in the authorization redirect and `code` and `state` in the callback URL. Restrict them to those protocol steps. The completion URL, logs, audit and status payloads must omit them. Access and refresh tokens stay outside every browser URL and response, including errors. | Inspect the authorize redirect, callback, completion redirect, access/application logs and audit records at their respective boundaries. Retain the single-use, PKCE and session-binding checks. |
| D4, D7, D9 | A worker can outlive the permission check that enqueued its run. Check the agency and client are active when claiming sync or refresh work and before persisting its results. A subsequent archive or suspension must still allow an already requested teardown to finish. | Archive the client after enqueue and during a fetch. Verify no new records or token version are installed, the other client still syncs, and pending purge completes. Test denial of a late callback after the initiating membership loses its manager role. |
| D6, D8, D9 | Specify outcomes for both token types and all outstanding versions. Record external revocation separately from local destruction and purge. Keep one deadline across duplicate disconnect requests, retries and restarts. Make teardown safe to resume after revocation succeeds and the worker stops before recording its result. A bounded command requires invocation to meet the synthetic 72-hour target. | Test transient failure, unsupported revocation, and failure through the deadline using a controlled clock. Run the worker again at the deadline and verify zero provider records, cleared account fields, destroyed secret material, and the actual revocation outcome. If the worker first runs late, record the actual completion time. |
| D1, D5, D9 | Define how the synthetic provider observes the same grant state when FastAPI and `python -m app.connector_worker` run as separate processes. A process-local dictionary cannot establish this behavior. The synthetic provider's per-grant revocation proves isolation only for that adapter. Leave the live shared-grant policy to 010–013 following verification of each provider's revocation scope. | Exercise the worker through its command entry point with a disposable fixture shared across the processes. Show K1's credentials fail at the mock after teardown and fresh K2 and K3 requests still succeed for the same external account ID. |
| D2, D10 | Enumerate the writable columns for each transition. Purging K1 requires clearing `external_account_id` and `account_label`, which the proposed grant list does not name. Include the scoped foreign key for the reconnect target and classify the five tables in the existing `app.data_policy` registry. | Apply `0009` on disposable PostgreSQL, run a complete disconnect as `tracking_app`, inspect the stored rows, and verify denials for unrelated writes and cross-tenant references. Exercise the one-day transaction cleanup under `tracking_lifecycle` and run the existing registry checks against the migrated schema. |

After explicit owner approval, record the decision, reconcile the entry review, plan and tasks, then implement and verify `009-A` on this branch. Report the local commit, the exact checks and remaining gaps for independent review. The 72-hour target and retained history in `reconnect_required` apply to the synthetic slice. Specs 009-B through 009-D and live-provider policies remain open. Use disposable PostgreSQL for migration tests. Publication, native rollout and deployment retain their existing owner gates.
