## Findings and regression criteria

| Finding | Observed behavior on the reviewed commit | Required outcome |
|---|---|---|
| R009-01 · High · Reconnect loses the previous grant's revocation outcome | Reconnect succeeded while the provider temporarily failed to revoke the previous grant. A later disconnect returned `revocation=done` while the previous refresh token still worked at the synthetic provider. In `backend/app/services/connectors.py`, `_install` destroys the old secret at line 502, and `_finalize` inspects only non-destroyed versions at line 1070. | Retain a retryable, scoped revocation obligation for the superseded grant within the approved cleanup policy. Include all applicable versions in the connection-level result, including after a restart. Check both old and current grants at the provider and preserve other connections. At the deadline destroy local material and report any unresolved outcome accurately. |
| R009-02 · High · A superseded sync attempt can overwrite a successful attempt | A worker reclaimed the same one-page run after its lease expired and completed it. The original worker then wrote its earlier `last_successful_sync_at` over the completed result. `_claim` increments `attempt` at line 788, but the returned claim and the page-write fence do not verify ownership of that attempt. | Fence run completion, record writes, status changes and credential updates to the current running attempt. Test a delayed worker returning after its replacement, with distinguishable page data, timestamps and error results. This concerns the lease already shipped in 009-A. |
| R009-03 · High · A stale refresh can revoke the winning worker's grant | Two claims for one run refreshed an expired synthetic access token. The replacement installed a usable version. The older attempt found its original version destroyed and invoked grant disposal at lines 866 and 901. The mock revokes the whole grant, so the installed refresh token became unusable. | Check attempt ownership before and after refresh, including when a provider call is already in flight. Distinguish a superseded token on a still-current grant from a separate discarded grant. A fresh provider call with the winning credentials must succeed after the stale attempt returns. Retain the disconnect-race test. |
| R009-04 · Medium · The purge clock records the start of a batch | A controlled clock advanced from one second before the purge deadline to one second after it during revocation. The status response still returned `deadline_met=true`. `run_teardowns` passes its initial timestamp to `_finalize` at line 1122. | Observe completion time when finalizing each connection. Test a batch that starts on time but finishes late, and preserve the fixed deadline across retries. |
| R009-05 · Medium · Status offers mutations to a read-only caller | An analyst with client read access received `actions.disconnect=true`. `connection_view` uses connection state alone at line 649. The mutation endpoint still denies the operation. | Make the action flags reflect the requesting principal and connection state in both list and detail responses. Cover managers, analysts, client viewers and read service keys. |
| R009-06 · Medium · Unsupported grant disposal is treated as success | Two authorizations competed for one client/account. The losing install correctly returned `account_already_connected`. With revocation set to `unsupported`, its discarded grant remained active and no documented disposal-failure event was emitted. `dispose_grant` ignores the adapter's returned outcome at line 247. | Treat `unsupported` as an unresolved external outcome and preserve a sanitized indication for the operator. Test both returned `unsupported` and a raised transient error, with separate assertions for the winning and discarded grants. |
| R009-07 · High · One tenant's retrying revocation can delay another tenant's purge | Two agencies requested disconnect. Only the earlier request's provider revocation failed. Four worker passes with a batch size of one, five minutes apart, always selected the earlier request. The healthy connection stayed `disconnecting`. `_claim_teardowns` sorts by deadline and `_finalize` makes a pending row immediately eligible again. The same ordering applies when pending rows fill the default batch of ten. | Give unattempted eligible connections an opportunity to run while preserving retry and deadline handling. Verify the healthy connection reaches `disconnected` while the earlier one is pending, then verify the earlier request recovers or purges at its own deadline. |
