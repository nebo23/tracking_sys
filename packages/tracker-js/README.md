# First-party website tracker

A self-hosted native JavaScript module (ES2022, no runtime dependency, no bundler) that connects a client website to the specification 004 public collection routes under J1 strict opt-in. It is separate from the React dashboard. Specification 005 (D-033) defines its behavior; the backend applies every rule again, so the tracker never widens what the server accepts.

## What it does and does not do

- **Before an explicit consent action** it reads no storage, URL, referrer, cookie or form value, generates no identifier, sends no request and keeps no event backlog. Loading the module and registering DOM bindings is all that happens.
- **One permission rule.** A purpose is effective only while the collector reports it granted and its server expiry (`expires_at`, read against the response's `server_time`) has not passed, the visitor's latest choice still allows it, Global Privacy Control does not restrict it, and the fixed local lifetime has not ended. The rule is checked at every capture and again before every send, including retries. A grant's remaining lifetime is counted from the moment its request started, so network latency shortens the local deadline and never extends it; a grant reported without a valid expiry or server time is not effective. A purpose the visitor newly allows takes effect only when a consent or state request that started after that choice confirms it.
- `grant(choices)` sends the visitor's explicit choices once (`POST /collect/v1/{public_key}/consent`). Choices take local effect at once; the response can only enable purposes the latest choices still allow. A grant that only denies, with no known subject, sends nothing.
- `resume(choices)` is for a decision your banner or consent platform already holds. Purposes it no longer includes stop immediately, including while the state read is pending or fails; purposes it newly includes wait for that read to succeed, so a pending, failed or older answer never re-enables a withdrawn purpose. It then reads the stored token and asks `POST /collect/v1/{public_key}/consent-state`. It never grants, renews or recreates consent; unknown, withdrawn, expired or missing state stays blocked until a new explicit grant. Consent operations run one at a time; a `resume` (or `grant`) that waited its turn checks the latest choices again, and when a newer choice has replaced every purpose it was asked for it ends as `superseded` without reading storage or sending the subject token.
- `withdraw(purposes)` and `erase()` stop the affected purposes immediately, forget their cached server grant, discard affected queued events, and run after any pending consent request. A late grant response is reconciled per purpose with the latest choices, so withdrawing one purpose never revokes the others. A failed withdrawal is retried in memory and reported as `confirmed: false`. `erase()` can still reach a subject whose local lifetime has ended.
- A browser Global Privacy Control signal refuses `sale_or_share`, `ads.measurement` and `ads.personalization` grants before anything is sent, both when `grant` is called and again when a `grant` that waited behind other consent work issues its request (a signal that became active in between removes the restricted grants from that request, the remaining choices are still sent, and the result lists the removed purposes under `refused`; if nothing is left, nothing is sent and no subject is created), and keeps them disabled locally even when the subject granted them earlier. When the collector still reports such a grant, the tracker withdraws it through its existing consent source: one bounded request per round, and at most three consecutive failed rounds for one grant. A round starts when an answer requested after the previous round still reports the grant (after a transient failure, or after a later regrant), or when `grant` or `resume` receives a choice that GPC refuses for a subject the tracker already holds in memory, including when GPC filters every requested choice (the call still returns `nothing_sent` or `blocked`, and the empty local permission keeps tracking blocked). The tracker tells grants apart by the `expires_at` the collector reports: a routine refresh of the unchanged grant keeps an exhausted limit, and a distinct new grant gets its own. A new visitor's GPC-only choice creates no subject, storage access or request. After a reload, a subject known only from `sessionStorage` is not read for a GPC-only choice; its server grant is reconciled once a permitted `grant` or `resume` makes the subject known again. GPC never grants anything and introduces no jurisdiction profile beyond J1.
- After permission, `sessionStorage` (key `ts:v1:<public key>`) holds only the subject token, the granted-purpose snapshot and a fixed local expiry at most 24 hours after first storage, never extended. If storage is unavailable the tracker keeps the token in memory only. It uses no `localStorage`, cookie, fingerprint or cross-site identifier. `sessionStorage` survives reloads and may be copied into a window opened from the page; open links with `rel="noopener"`. Tabs do not share consent, and a remote withdrawal reaches an open tab at its next state read (at most 60 seconds while collecting). Automatic state reads (refresh timer, visibility change, page restored from the back/forward cache, `refresh()`) need current host permission: after a full withdrawal the token stays in memory only so that `erase()` can reach the subject, and no background request carries it. After the local lifetime ends, no request uses the token (no state read, refresh timer or restored page), the stored record is removed and a new explicit grant is needed. An automatic state read that was outstanding while a consent write (`grant`, `withdraw`, `erase` or a GPC withdrawal) was on the wire is not adopted, because the collector may have processed the two in either order; the write's own answer counts, and `refresh()` returns `false` for such a read. A read that was answered but not adopted is repeated once the pending consent operations finish, unless a newer answer arrived meanwhile and only while the host still allows a purpose.
- Built-in capture: `trackPageView()`, `trackLinkClick(anchor)` and `trackForm(formKey, form)`, plus optional click and submit bindings. URLs are minimized in the browser with the same rules as the server (campaign parameters with analytics, click identifiers only with attribution, email-like and card-number values removed). A managed link's `ts_link` is moved from the URL into the envelope `link_id`; it is read from the current URL for every new event, so single-page routes each carry their own reference (or none), while a retried event keeps its original bytes. It is a link reference, never a visitor identifier.
- Forms: only configured fields of the classes `form.option`, `form.code` and `form.quantity` are considered. Password, hidden, payment (`cc-*`), one-time-code, email, telephone, textarea and unconfigured controls are excluded from their descriptors before any value is read. The tracker never uses `FormData` on a whole form. Email, phone, name and free text wait for specification 006.
- Transport: one event per `fetch` request with `credentials: "omit"`, no referrer and `text/plain` JSON (a CORS simple request). The in-memory queue holds at most 20 events and 128 KiB for 60 seconds; each event gets at most three attempts with jittered delays of about 1 and 4 seconds, or a readable `Retry-After` within the queue lifetime. Each queued event records every purpose its bytes depend on (analytics, plus attribution while a URL keeps a click identifier) and the server grant it was captured under; narrowing permission drops affected events, and an event already on the wire is never attempted again, even after a later regrant. A request still pending when its event's 60 seconds end is aborted, so a stalled connection cannot hold back later events. Consent and state requests are aborted after 10 seconds, and the queue never waits for a state read beyond its oldest event's lifetime. A `202` is a generic acknowledgement, not proof of storage. Navigation and form submission never wait for telemetry, and tracking errors never reach the page.

This is not general personal-data detection, not a guarantee of delivery, and not legal compliance advice.

## Installation

1. Register a browser ingestion source for the client (exact site origins and the notice digest) and register each form with `PUT .../collection-forms/{form_key}`. The page configuration below must not exceed the registered form.
2. Copy `src/tracker.js` and `src/minimize.js` to your own site's static assets. No CDN is selected; serve the files from your origin with a version in the path.
3. Allow the collector origin in `connect-src` if your site uses a Content Security Policy. Initialize the tracker from a same-origin module file, as the example does, so the policy needs no `'unsafe-inline'`.
4. Connect your consent banner to `grant`, `resume`, `withdraw` and `erase` (see [examples/install.html](examples/install.html) and its module [examples/install.js](examples/install.js); both are exercised unchanged in Chromium and Firefox by `test/browser/install-example.browser.test.js`).

```js
import { createTracker } from "/assets/tracker-0.5.4/tracker.js";

const tracker = createTracker({
  collector: "https://collect.example.test", // exact origin of the Tracking System API
  publicKey: "pk_...", // public source key; never an ingest or read service key
  forms: { lead: { fields: [{ name: "plan", data_class: "form.option", options: ["basic", "pro"] }] } },
  bindings: { links: "a[data-track]", forms: { lead: "#lead-form" } },
});
```

Single-page applications call `trackPageView()` after each route change; the History API is not patched.

## Development and tests

Dependencies are project-local (D-011): Playwright 1.64.1 is the only development dependency, locked in `package-lock.json`. Browsers install into this package's `node_modules` (never a global cache):

```powershell
npm ci
npm run install:browsers
npm test                 # Node built-in test runner: state machine, storage, transport, parity
npm run test:browser     # real Chromium and Firefox through Playwright
```

`test/fixtures/parity.json` holds shared minimization fixtures whose expected values come from the Python contracts; `backend/tests/test_tracker_parity.py` asserts the same file. The backend journey test (`backend/tests/integration/test_tracker_journey.py`, enabled with `TRACKING_RUN_BROWSER_TESTS=1`) runs `test/e2e/journey.js` and `test/e2e/parity-page.js` against the real API on loopback and a disposable database.
