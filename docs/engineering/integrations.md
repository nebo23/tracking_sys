# Bookings, CRM stage changes and WhatsApp referrals (specification 015, second round)
Status: 015-D (integration sources, Cal.com bookings, the provider-neutral signed webhook and CRM deals) and 015-E (WhatsApp Cloud API referrals) are implemented under D-068 against synthetic senders and fixture tests. Every source type is off by default. No call to Cal.com, a CRM or Meta has been made, and no migration has run on the native `tracking_sys`. Live callbacks need an HTTPS-hosted API (020) and owner accounts, which remain separate decisions. Design: [design-015b.md](../../specs/015-business-integrations/design-015b.md); evidence: [evidence.md](../../specs/015-business-integrations/evidence.md). Payments are in the [payments guide](payments.md).

## Integration sources
Owners and Admins manage a client's integration sources; every change is audited (`integration.created`, `integration.updated`, `integration.secret_replaced`).

| Kind | Setting | Secret | Callback |
|---|---|---|---|
| `cal_com` | `TRACKING_INTEGRATIONS_CALCOM_ENABLED` and a current `calcom.webhooks` rule | The secret the client sets in Cal.com (16-256 printable characters), entered once and never returned | `POST /integrations/cal-com/isk_<43 characters>`, signed in `x-cal-signature-256` |
| `signed_webhook` | `TRACKING_INTEGRATIONS_WEBHOOK_ENABLED` | Issued by the platform (`whsec_...`) and returned once | `POST /integrations/webhook/isk_<43 characters>`, signed in `X-Tracking-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body">` within five minutes |

Routes: `POST`, `GET .../integration-sources`, `PUT .../integration-sources/{id}/secret` (a Cal.com source takes `{"secret": ...}`; a signed webhook source sends `{}` and gets a new issued secret), `PATCH .../integration-sources/{id}` (`name`, `status`). A replaced secret stays valid for 24 hours. In Cal.com, the client adds a webhook with the API's HTTPS origin followed by the callback path, the triggers Booking Created, Requested, Rescheduled, Cancelled, Rejected and Meeting Ended, and the same secret.

Every callback answers `200 {"status": "received"}` once verified; an invalid signature, an unknown, disabled, malformed or other-kind key all answer `401 invalid_signature`; with the kind off, `503 integration_unavailable`; without the token keyring, `503` for every key. Bodies are limited to 64 KiB. Each verified delivery leaves one row in `integration_deliveries` (body digest, receipt time, outcome `applied`, `duplicate`, `ignored` or `invalid`, reason); a repeated delivery changes nothing.

## Bookings
A booking is a chain of provider booking IDs: a reschedule adds the new ID, a cancellation of the current ID cancels the booking, and a cancellation of an ID that was rescheduled away is ignored. Booking IDs belong to the source that delivered them (review finding R006): two sources of one client, for example two booking tools sending to two signed webhook sources, may both use `booking-1`, and each keeps its own booking. A reschedule or cancellation reaches only bookings of the same source. To move a Cal.com account's webhook to new credentials, replace the source's secret rather than creating a second source, which would start a separate namespace. The status (`requested`, `scheduled`, `cancelled`, `rejected`, `completed`) comes from the latest event about the current ID, so the order of deliveries never changes the result. A booking is never revenue and never a sale. Nothing personal is stored: no attendee, email, phone, answer, note or meeting link.

`GET /agencies/{a}/clients/{c}/bookings` (`client:read`) returns the totals by status, the linked count and the newest 500 bookings.

**Lead links.** To link a booking to a visitor, the booking page carries the visitor's 004 subject token (`sbj_...`) in a hidden booking field named `ts_subject` (the signed webhook contract uses `booking.subject_token`). The booking is linked only while that subject's `attribution` consent is granted; otherwise the delivery records `subject_unknown` or `consent_missing`. The link follows the consent afterwards too (review finding R003): a withdrawal or denial detaches the subject's bookings at once; an expired grant stops counting immediately on every read (`totals.linked` and each booking's `linked`); and a grant made after a lapse restores nothing until a later delivery carries the token again. An exact replay of an earlier delivery is a no-op and never restores a link. When a later event joins two chains, a link moves with them only while its consent is granted. The token is never stored. Erasing the subject, or its lifecycle expiry, clears the link (both columns together) and keeps the booking (review finding R002). Person-level leads wait for 006.

**Signed webhook bookings.** `{"type": "booking.created" | "booking.requested" | "booking.rescheduled" | "booking.cancelled" | "booking.rejected" | "booking.completed", "id": "<event id>", "occurred_at": "<ISO 8601 with offset>", "booking": {"id", "previous_id" (reschedules), "event_type", "start_at", "end_at", "subject_token"}}`. Use it for booking tools other than Cal.com, through an automation tool that can sign requests.

## CRM stage changes
A CRM or automation tool sends `{"type": "deal.stage_changed", "id", "occurred_at", "deal": {"id", "pipeline", "stage", "previous_stage", "amount", "currency", "payment_reference"}}` to a signed webhook source. Text values have 1-128 printable characters; an email address, an international phone number or a card number refuses the delivery (`invalid_deal`). Amounts are decimal strings in major units of an allow-listed currency. **A change is a partial update** (review finding R007): it always carries the stage and may carry the amount with its currency and a payment reference. Each part keeps the value of the change with the latest occurrence time that supplied it, and an omitted part keeps the latest supplied value. At the same instant, the larger value wins (the stage text, then the pipeline and previous stage; the currency code, then the amount; the reference text). Every delivery order of the same changes therefore ends in the same deal. The amount and its currency always move together. A value cannot be removed through the contract: send the corrected value in a later change.

A stage change never becomes revenue. Owners and Admins approve won and lost stages (`POST`, `GET`, `PATCH .../crm/stage-rules`, `{"pipeline", "stage", "outcome": "won" | "lost"}`, audited `crm_rule.created` and `crm_rule.updated`). `GET .../crm/deals` (`client:read`) shows each deal as `open` (no rule), `lost`, `won_unverified`, or `won_verified` when its `payment_reference` equals the operation ID of a posted sale in the client's verified revenue (for a Paymob sale, the Paymob transaction ID). `?include_amounts=true` needs `finance:read` and adds the amount, the currency and the linked sale. The `totals` count every deal of the client. The `deals` are one page, newest first received and then by ID, of at most `limit` deals (1-500, default 500). `has_more` says whether another page follows, and `next_after` (present only then) is the cursor to pass as `after` for it. Every deal appears exactly once across the pages (review finding R008). Amounts are never added up across deals or currencies.

## WhatsApp referrals
| Setting | Meaning |
|---|---|
| `TRACKING_WHATSAPP_ENABLED` | Off by default; usable only while the `whatsapp.cloud_api` rule is current |
| `TRACKING_WHATSAPP_APP_SECRET` | The Meta app secret that signs notifications (16-256 characters, ignored `.env` only) |
| `TRACKING_WHATSAPP_VERIFY_TOKEN` | The token of the endpoint handshake (16-256 characters, ignored `.env` only) |

In the Meta app, the webhook URL is the API's HTTPS origin followed by `/integrations/whatsapp/webhook`, with the verify token, subscribed to the `messages` field. `GET` answers the handshake only for `hub.mode=subscribe` and the verify token. `POST` verifies `X-Hub-Signature-256` (401 otherwise) and accepts bodies up to 3 MiB.

Owners and Admins register each client's WhatsApp Business phone number ID (`POST`, `GET`, `PATCH .../whatsapp-numbers`, audited). **A registration is a claim, not a binding (D-070, review finding R004).** Every client's notifications reach the platform's one Meta app, and an agency's authority over its own workspace does not prove that it owns a provider number. A new registration therefore starts `pending` and routes nothing. Several clients may hold pending claims for one number, so a first claim by another agency neither captures the number's messages nor blocks the real owner; a client holds at most one unrevoked claim per number (`409` otherwise).

The platform operator, who acts outside the agency roles, verifies a claim after checking out of band, in Meta Business Manager, that the number belongs to that client's WhatsApp Business Account and that the account was onboarded to the platform's Meta app:

| Command | Effect |
|---|---|
| `python -m app.whatsapp_binding list [--status pending\|active\|disabled\|revoked\|all]` | JSON list of claims: claim, agency and client IDs, phone number ID, status and times |
| `python -m app.whatsapp_binding verify --claim <uuid> --confirm` | The pending claim becomes the number's `active` binding with `verified_at`; refused (`number_already_bound`) while another binding of the number is verified |
| `python -m app.whatsapp_binding revoke --claim <uuid> --confirm` | The claim or binding becomes `revoked` and routes nothing; the number is free for another verified binding |

A number has at most one verified binding (a partial unique index). To move a number to another client, the operator revokes the current binding and then verifies the other client's pending claim; messages already stored keep their client. Agencies may switch only a verified binding between `active` and `disabled`; a pending claim answers `409 verification_required` and a revoked one `409 claim_revoked`. Operator actions are recorded on the claim (`status`, `verified_at`, `updated_at`), not in the agency audit log, whose actors are agency members. Nothing here calls Meta; a provider-verified binding through Meta's own onboarding is a later option for production.

For every inbound message of a verified, active number, only the Click-to-WhatsApp referral is stored: the source type (`ad`, `post` or `other`), the ad ID and whether a click ID was present. A message without a referral is recorded as unknown. Phone numbers, names, sender IDs, message text, ad copy, media URLs and click IDs are never stored or logged, and no conversation is correlated with a person. Messages of unregistered numbers and status notifications store nothing; Meta's retries are deduplicated. Each message of a signed batch is read on its own (review finding R009): a source type that is not `ad` or `post`, including a list or object, is recorded as `other`; a timestamp outside 2015-2099 is stored as unknown; and an item that is not an object or has no usable ID is skipped. One malformed message therefore never discards its siblings or makes the route fail. An invalid signature still answers 401, and a storage failure still answers a server error, which Meta retries.

`GET .../whatsapp/referrals?since=YYYY-MM-DD&until=YYYY-MM-DD` (`client:read`, UTC days, at most 92, default the last 30) returns the total, the unknown count and the counts per source type and ad ID.

## Lifecycle
`python -m app.lifecycle` deletes, as `tracking_lifecycle`: integration deliveries 30 days after receipt (`TRACKING_INTEGRATION_DELIVERY_RETENTION_DAYS`), retired integration secrets, bookings with their events 395 days after their last update (`TRACKING_BOOKING_RETENTION_DAYS`), CRM deals 395 days after their last update (`TRACKING_DEAL_RETENTION_DAYS`) and WhatsApp messages 395 days after receipt (`TRACKING_WHATSAPP_MESSAGE_RETENTION_DAYS`). Each period may be shortened, not extended. Sources, rules and numbers stay until workspace deletion (017).

## Before any live use
- An HTTPS-hosted API (020) and owner Cal.com and WhatsApp accounts for live checks, separately approved. The Cal.com check confirms the signature encoding, the hidden-field prefill and whether an old ID is cancelled at a reschedule.
- Native `tracking_sys` migration of `0023` to `0025`, and deployment, which remain separate owner decisions.
